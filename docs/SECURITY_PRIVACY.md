# Security and privacy

Kerneon is created and published by **Ryan Horth**.

Kerneon is a local-first monitor with three explicit opt-in boundaries: AI analysis, allowlisted Surge remediation, and LAN Remote Link.

- Runs as the current user with an `asInvoker` manifest.
- Kerneon itself does not install a service, driver, certificate, browser extension, or firewall rule. If the user explicitly chooses **Enable startup**, Kerneon writes one current-user `HKCU\\Software\\Microsoft\\Windows\\CurrentVersion\\Run` value pointing to its own executable; the in-app setting can remove it. Optional frame proof detects a separately installed official Intel PresentMon service.
- Does not inject code, hook games, read game memory, or use undocumented timer/HPET modifications.
- Does not terminate or suspend processes. Manual and Surge scheduling controls are restricted to Below normal, Normal, and Above normal; High and Realtime are refused.
- Does not upload telemetry by default or require an account. An AI request occurs only after the user connects an API key and clicks Generate.
- AI sends current/aggregate resource measurements and anonymous process metric labels; it excludes process names, executable paths, hostnames, adapter names, usernames, and IP addresses.
- Uses a stateless OpenAI Responses API request with strict structured output and no model tools. Generated advice cannot invoke application actions.
- Stores the optional API key in Windows Credential Manager. It is not written to settings, logs, exports, or source files.
- Does not download or execute code at runtime. AI responses are bounded JSON text rendered as advisory cards.
- Uses Windows ICMP only when latency monitoring is enabled and only for the configured target.
- Reads local process, registry, performance-counter, network-interface, volume, and OS information through documented Windows APIs.
- Stores settings, logs, and user-requested exports in the current user's profile.

Diagnostic exports are created only by explicit user action. Exported text replaces the username, home path, and IPv4-like strings. The export contains a system summary, provider status, settings, and sanitized logs; it does not contain a process list or executable paths.

The process-detail page exposes path/PID tools and safe scheduling preference. It does not expose termination, suspension, affinity, service, registry, driver, memory-cleaner, or game-file mutations.

Surge uses documented Windows process information APIs for execution power QoS, scheduling, memory priority, and affinity. Guarded power-policy changes require AC power and workload evidence. Explicit Aggressive mode creates a separate temporary scheme through documented `powercfg` operations; it does not edit the user's existing scheme. Each action is written to a flushed JSONL record before execution. An active-session snapshot includes process path and creation time as well as PID, preventing rollback onto a recycled PID. Prior and temporary power-plan GUIDs are stored atomically for interrupted-startup recovery. If journaling fails, mutation is refused.

The separately consented Tuning Lab is off by default and cannot arm “Auto with Surge” unless a direct manufacturer-supported control is detected. Its NVIDIA adapter dynamically uses only public NVML controls that return a current value and explicit allowed range. Every requested value is revalidated immediately before the write; a multi-control failure attempts to restore earlier sub-writes. An atomic hardware snapshot remains on disk until exact rollback succeeds. The current preview requires a user-approved elevated restart and clearly labels that session. Remote Link remains available for paired monitoring and its existing fixed allowlist, local grants, origin checks and session expiry still apply; it exposes no arbitrary path, command, register, firmware, I2C, DLL injection, game-memory, or kernel-driver route. A signed on-demand broker remains required production hardening before broad commercial distribution so hardware mutation is isolated from the ordinary UI and LAN listener.

Remote Link binds only the selected private IPv4 address after the user enables it; it does not listen on every interface. Pairing uses a random 128-bit URL-safe QR credential or a rate-limited six-digit manual fallback, then issues a separate random eight-hour HttpOnly/SameSite-Strict device session. The QR keeps its credential in the URL fragment, which passive HTTP previews cannot transmit; browser JavaScript exchanges it locally and proceeds straight to the dashboard without asking for digits. The public QR rotates after the first valid exchange. The consumed credential remains valid for only 45 seconds as a bounded camera-preview-to-browser handoff, covering phones that isolate preview and browser cookie stores, and is then rejected. A manual pairing, New pairing, or Remote Link shutdown clears that grace immediately. “New pairing” also revokes every existing device cookie, pending command, general control grant, and screen peer before publishing new credentials. Host validation resists DNS rebinding.

Mutation requires the device session, exact same Origin, a custom header, an explicit allowlist, and a local control grant. The user can choose 15 minutes or “Until revoked”; the latter is runtime-only and is cleared when Remote Link stops, the app exits, pairing is reset, or access is revoked. Device authentication still expires after eight hours. Commands and local grant changes are serialized and written to an fsynced audit log.

Kerneon Session uses native Windows display capture, limits previews to 1280 pixels wide at approximately eight JPEG frames per second, and sends frames through a WebRTC DTLS data channel. A second reliable DTLS data channel carries bounded monitor-selection and input messages. Screen view and keyboard/pointer control have separate local Off/15-minute/Until-revoked grants. Input is rate-limited, normalized to the selected monitor, and ignored if the device session or local input grant is invalid. A global in-app sharing pill and tray tooltip remain visible while a grant exists; revoking view also revokes input. Resetting pairing or stopping Remote Link closes every peer connection.

Remote Link's pairing pages, cookies, API requests, and WebRTC signaling currently use HTTP and therefore are not confidential or authenticated against an active hostile observer already on the LAN. WebRTC encrypts screen frames and input after the peer connection is established, but the product still must be used only on a trusted private network and never port-forwarded. The endpoints intentionally omit arbitrary commands, file access, Windows credential collection, clipboard transfer, and a shell. Kerneon never asks for the Windows account password; a pairing code alone is not authorization for general control, screen pixels, or input.
